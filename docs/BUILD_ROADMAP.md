# 机器人 Agent 框架分阶段构建路线

更新日期：2026-10-07。当前阶段：**P0 已完成；P2–P5 的 Agent 层软件部分已有 L0 实现（[AGENT_LOOP.md](AGENT_LOOP.md)），退出条件仍待仿真验收。下一步是仿真基座和真实模型验收；实机轨 R1 并行，仍在等 G1 连接信息。**

本路线负责"按什么顺序构建"。各模块的实时状态以 [PROJECT_STATUS.md](PROJECT_STATUS.md) 为准，待决问题以 [OPEN_QUESTIONS.md](OPEN_QUESTIONS.md) 为准，目标分层与接口见 [DETAILED_ARCHITECTURE.md](DETAILED_ARCHITECTURE.md)。

## 1. 目标与方向

目标：构建**面向通用机器人本体的 Agent 系统**，具备长程任务拆解、子技能编排、技能执行监测、Loop 回环反馈和世界状态维护五项能力。

2026-10-06 的方向决策：

1. **仿真与实机并行**，两条轨道共用同一套 SkillSpec 和执行语义，只是 `provider` 和 `evidence_level` 不同。
2. **G1 为首个本体**。
3. **适配多种本体**：Agent 层不依赖具体本体，必须用第二种本体验证。

## 2. 目标架构

```text
            ┌────────────── 外环：目标级重规划 / 请求人工 ────────────────┐
Goal ─▶ 任务分解层（层级任务树，执行到时再展开子任务）                   │
            │        ▲ 中环：子树局部修复（保留已成功步骤和世界状态）     │
            ▼        │                                                    │
        编排层（条件 DAG / 行为树；抽象技能，带前置条件和效果）           │
            │        ▲ 内环：重试 / fallback                              │
            ▼        │                                                    │
        执行内核（Runtime：执行身份、fencing、资源、持久恢复、证据）      │
            │                                                             │
            ▼                                                             │
        本体适配层（Embodiment Profile → ROS2 Action / Unitree SDK / 仿真）
            │                                                             │
            ▼                                                             │
        执行监测（进度反馈、不变量、停滞、基于观测的独立验证）────────────┘
            │  ▲
            ▼  │
        世界状态（实体、关系、机器人状态；时间、坐标系、置信度、来源、有效期）
             ▲ 感知技能写入、技能效果更新、超时失效
```

各层的权威划分不变：
- LLM 只产生计划候选；
- Runtime 是任务和资源状态的权威；
- 控制端令牌决定谁有物理执行权；
- 独立 verifier 判断目标是否完成；
- 硬件急停走本体自身的安全链路。

## 3. 双轨推进原则

| 原则 | 说明 |
|---|---|
| 同一契约 | 仿真和实机实现同一套 SkillSpec、执行状态机、反馈和停止证据语义。Agent 层不知道当前跑在哪条轨道上 |
| 证据分级 | 每条执行、观测和验收记录都带 `evidence_level`（`software_integration` / `simulation` / `hardware_observation`）。仿真证据只能关闭契约和算法问题 |
| 仿真先行，不等实机 | 每个主线阶段先在仿真里达到退出条件。实机轨被外部输入阻塞时，不阻塞仿真轨 |
| 实机对齐 | 实机轨按 R1→R4 逐级推进，每级对应一个已经在仿真里通过的阶段。实机发现的偏差回写到契约和仿真 |
| 不用替身 | mock 或替身响应不能作为任何等级的验收证据。AI 调用必须使用真实模型 |
| 支线服务主线 | 支线工作只在主线阶段需要时推进 |

## 5. 各阶段内容

### P0：可运行骨架与执行内核（已完成）

已有内容：
- 任务和步骤契约、DAG 校验、资源账本、结果判定、DBOS 持久恢复；
- HTTP 技能协议和本地文件技能；
- 模型适配与上下文层、应用层动作、只读 UI；
- HTTP fencing 和停止核对。

证据全部为 L0，见 [PROJECT_STATUS.md §7](PROJECT_STATUS.md)。

### P1：工程基线

| 交付物 | 退出条件 |
|---|---|
| 标准开发环境：WSL2 或 Linux，Ubuntu 22.04 + ROS2 Humble + Python 3.10 | 按 README 能从零安装；`robot_agent` 可以导入。如果确定需要原生 Windows，就把 `fcntl` 文件锁和 `killpg` 抽成可替换的实现 |
| `.gitignore` 和仓库清理 | `node_modules`、`.runtime`、`__pycache__`、`egg-info`、`dist` 和测试产物移出版本库；验证证据保留在 `docs/validation` |
| 全量回归基线 | 在标准环境中跑一次全量离线回归，结果归档，取代各文档里零散的测试数字 |
| CI | 离线 Python 回归加 UI 构建自动运行；真实模型和仿真测试单独触发 |

这一阶段不依赖设备，应该最先完成。

### P2：本体抽象与仿真基座

| 交付物 | 说明 |
|---|---|
| 仿真器选型 | 至少比较 Isaac Sim/Lab 和 MuJoCo 类方案。评估维度：G1 模型支持、与实机 SDK/DDS 接口的一致性、相机和深度仿真、GPU 需求、许可。结论写入 DECISIONS |
| Embodiment Profile v1 | 描述本体能力、资源清单与互斥约束、坐标系、安全限值、技能实现清单。G1 是第一份 Profile |
| 抽象技能与本体绑定 | Agent 层只看到抽象技能，比如 `observe_state`、`stand`、`stop`、`move_velocity`、`navigate_to`。Profile 把它们绑定到具体实现 |
| 技能适配层 | ROS2 Action 适配器：execute、query、cancel、feedback 映射到 Action。仿真 provider 和实机 provider 实现同一套适配接口 |
| `evidence_level` 字段 | 执行、观测和验收记录都带等级；观察 API 和 UI 区分显示 |
| G1 仿真环境与首批技能 | 在仿真里跑通状态读取、站立和停止、速度移动 |

- **仿真退出条件：** Agent 提交的任务经过抽象技能、G1 Profile 和仿真 provider 完成执行，记录完整且标为 `simulation`；取消和停止能拿到停止观测。
- **实机并行 R1（只读接入）：** 拿到 [G1 接入契约](G1_INTEGRATION_CONTRACT.md) 列出的 6 项连接信息，实现只读状态采集，归档原始消息和来源信息，记录断流和恢复。不发送任何运动指令。

### P3：世界状态与技能契约

| 交付物 | 说明 |
|---|---|
| WorldState 模型 | 实体、关系、机器人状态和地图版本。每条事实带时间戳、坐标系、时钟域、置信度、来源证据和有效期 |
| 观测有效性 | 分为 valid、stale、unavailable、invalid；区分"最近收到"和"采样仍新鲜" |
| 更新机制 | 感知技能写入观测；技能效果更新预期状态，等观测确认后才转为事实；冲突保留来源，不覆盖 |
| 技能前置条件和效果 | 用世界状态谓词表达。派发前检查前置条件，完成后对照观测检查效果 |
| WorldStateProvider（原 CTX-5） | 进入上下文包前检查时间、坐标系和地图版本的一致性 |
| 地图和 TF 版本 | 版本变化时，受影响的世界状态和计划进入待重验状态 |

- **仿真退出条件：** 仿真里的位姿和物体状态进入 WorldState；断流后变为 stale；技能在前置条件不满足时被拒绝派发；完成后的效果由观测确认。
- **实机并行 R2：** G1 的实际状态流进入 WorldState，在真实断流和时间跳变下判定正确。

### P4：执行监测与三层反馈环

| 交付物 | 说明 |
|---|---|
| 进度和反馈协议 | 技能协议增加 feedback，Runtime 持久保存并开放给监测器 |
| 监测器 | 不变量监测（订阅世界状态）、停滞检测、超时检测 |
| 基于观测的独立 verifier | 验收读取世界状态和传感器，不依赖执行技能的自述 |
| 中环：局部修复 | 替换 `revise` 的整计划替换方式：保留已成功的步骤和世界状态，只修复失败的子树；不可逆技能按前置条件重新判断能否执行 |
| 世界变化触发 | 前置条件或不变量失效时，暂停受影响的分支并进入修复 |
| 补偿与人工接管 | 定义补偿技能、触发条件、补偿结果和人工处理终态；补偿本身也是有身份、有资源、有证据的执行 |
| 统一重试归属 | 合并框架、行为层、驱动和模型的重试预算；不可重入动作只查询原 execution ID |
| 故障矩阵 | 覆盖 [DETAILED_ARCHITECTURE.md §13.2](DETAILED_ARCHITECTURE.md) 的全部条目 |
| 心跳 | 区分 API 在线、worker 在线、机器人在线、机器人已停止四个指标 |

- **仿真退出条件：** 注入物体掉落、路径阻塞、传感器断流等故障后，三层环分别正确响应；局部修复保留了已完成的进展；补偿成功、补偿失败和需要人工处理三种情况都有持久证据。
- **实机并行 R3：** 接入第一项运动技能（建议从速度移动加停止开始），满足执行身份、令牌、查询、取消和独立停止观测，确认硬件急停链路。不能把 SDK 返回 code=0 当成已静止。

### P5：长程层级任务拆解

| 交付物 | 说明 |
|---|---|
| 层级任务树 | 目标→子任务→技能三层；子任务有自己的完成条件和 verifier |
| 按需展开 | 子任务执行到时，用当时的世界状态再展开 |
| 条件编排 | 条件节点或行为树后端，按 G1 技能需求选定 |
| 规划输入 | 规划读取世界状态、本体 Profile 和抽象技能目录 |
| 评测集 | 在仿真中建立多任务族数据集（导航、开抽屉放物、多房间搜寻等），按执行结果评价，不用模型自评 |

- **仿真退出条件：** 真实模型在至少 3 个任务族上生成层级计划并执行完成；每个结论都能追溯到原始响应、计划版本、技能结果和最终验证。
- **实机并行 R4：** G1 的一个移动或导航类任务族在实机上完成闭环。

### P6：多本体验证

| 交付物 | 退出条件 |
|---|---|
| 第二份 Embodiment Profile（建议先在仿真中做轮式底盘或固定机械臂） | Agent 层和 Runtime 代码不改，只新增 Profile 和适配器 |
| 能力差异处理 | 同一目标在不同本体上生成不同的计划；某个本体没有所需能力时明确拒绝或请求人工 |

### P7：场景验收

- 陌生环境自主探索和目标趋向导航。
- G1 把红色方块放进抽屉（[DETAILED_ARCHITECTURE.md §7](DETAILED_ARCHITECTURE.md)）。

两个场景都先在仿真通过，再到实机验收。具体测量指标按场景另行定义，场景通过只关闭对应的验收项。

## 7. 当前下一步

2026-10-07：Agent 层的世界状态、技能世界契约、监测、三层反馈和任务分解已有 L0 实现，见 [AGENT_LOOP.md](AGENT_LOOP.md)；2026-10-12 任务分解按 [L0 规划层设计](../L0%20规划层设计.md) 重写为 TaskPlan。接下来按优先级：

2. **真实模型：** 对 L0（`task_planning`、`task_acceptance`，见 `tests/test_l0_live.py`）和 `repair` 方法做 live 验收，生成证据文件。
3. **P1：** `.gitignore`、处理过期测试、CI；为 ROS2 和仿真确定 Linux/WSL2 标准环境。
4. **R1：** 继续等 G1 连接信息；信息到位后做只读采集，写入 WorldState。
